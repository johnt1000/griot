# Roadmap

What is planned, and — more usefully — what was considered and turned down,
with the reasoning. Shipped work is in the [changelog](CHANGELOG.md).

## Now

What blocks a 1.0 tag. griot works, is used daily and is published on PyPI
(`pipx install griot-rag`, since 0.2.0); what "done" still means is this:

- **End-to-end MCP validation in a real project.** An agent calling
  `griot_search` against a real index, with the logs and `griot stats` output
  read afterwards to decide what to improve. A first stretch of about six
  weeks of real use has been read, and it changed the priorities: the main
  problem was not retrieval but that agents with the server attached mostly
  did not search. What followed is in the changelog: the server now tells
  the agent when to use it, the installer registers it for every project and
  offers to pre-approve the read-only tools, search can be narrowed and its
  results say where, when and who, and `griot stats` reports the state of
  the index instead of only activity in a window. What remains is reading a
  second stretch of use, after those changes, to see whether agents search
  on their own now and to decide about the two protocol gaps below.

## Next

What the rounds of 2026-10-06 left open is done: the bugs they found are fixed (#61, #62, #63), and so are the debts recorded at their close (debts 37 to 52 in [lessons and debts](docs/lessons-and-debts.md)). Golden-set cases keep their search mode and are searched as readers search, and the measurement that made hybrid the default can be run again (`scripts/measure-search-modes.py`).

Nothing else is queued; what comes next is chosen from the list below.

## Considered, not scheduled

- **Formalize two development-process patterns as Claude Code tooling — built locally, not shipped.** A 2026-09-02 review of this project's own recurring pitfalls against what Claude Code's skills/subagents/hooks system can do identified two candidates worth their maintenance cost, and rejected a third. Both candidates now exist as git-ignored, per-maintainer tooling under `.claude/`; neither is part of the package:
  - **A post-edit hook on `mcp_server.py`** that opens a real in-memory MCP client and smoke-tests every tool/prompt after a change. Justified by a pattern that has already cost real debugging time four separate times: a unit test and the implementation it tests can share the same wrong assumption and agree with each other, so only a call through the actual protocol catches the mismatch (wrong async wrapping, an unannotated `ctx` leaking into the input schema, a prompt describing a filter parameter that doesn't exist). Built as a local hook. Its limit: it lists the tools and prompts and renders the prompts, but never calls a tool, so it cannot catch a defect in what a tool does at runtime, such as a concurrency or lifecycle problem. Those need a real protocol call written for the case.
  - **A `.claude/agents/` subagent definition formalizing the code-reviewer half of the mandatory red/green/review cycle** (CLAUDE.md, "Fluxo de desenvolvimento") — codifying that the reviewer must be a different agent than the implementer, and giving it this project's specific review checklist (does it match the plan's scope, did a `None`-handling fix sweep every consumer, was an MCP change verified by protocol). Smaller payoff, since the discipline is already followed manually; formalizing it mainly protects Workflow-orchestrated changes from silently skipping the review step. Built as a local subagent definition.
  - **Rejected**: a codified multi-agent documentation-audit workflow (like the one that produced these findings). It happened once in this project's history, for a one-time "prepare for public release" reason — not a recurring task — so `/code-review` with ad-hoc personas already covers the next time this is needed without a maintenance commitment.

- **Platform adapters built ahead of confirmed demand.** Four of the five (GitLab self-hosted, Bitbucket Cloud, Azure DevOps, Gitea/Forgejo) have only ever been exercised against mocked HTTP — only GitHub has run against a real account. Kept rather than trimmed because each is small, behind one common interface, and covered by tests, unlike the removed dashboard's cost profile (see [lessons and debts](docs/lessons-and-debts.md#measure-before-deciding-whether-a-component-earns-its-place)). If one goes unused after the PyPI release, removing it is a one-file deletion, not a design change — but "built ahead of demand" is worth naming rather than leaving implicit.
- **More CI steps.** The pipeline runs tests (3.10, 3.13 and 3.14 on Linux, 3.13 on macOS), a gitleaks scan over full history (merge commits included), and a build that installs the wheel in a clean environment. Deliberately not added yet: a linter (the codebase has no style CI and adding one now would produce a large mechanical diff over code that is being actively changed) and coverage reporting (a number that invites optimising the number). Each is a one-job addition when the reason for it becomes concrete. **Rejected: a scheduled `pip-audit` job.** GitHub's Dependabot alerts read `uv.lock` against the same advisories and open the pull request that fixes one (they did, for `pyjwt` and `urllib3`, the day they were turned on); a second scanner would only repeat the warning.
- **Audit the whole history in CI.** CI already scans every commit for secrets; `scripts/audit-history.sh` also looks for files that never belong and for private terms in contents, names and messages, but only on the maintainer's machine, because the list of private terms is private by design. A CI job could read it from an encrypted repository secret. Not scheduled: the list would then live in a second place, and the pre-push hook already examines everything a push sends.

- **Broaden MCP protocol coverage** — griot uses 5 of the ~10 capabilities the protocol offers (tools, prompts, elicitation and, since 2026-10-06, resources and progress). **Resources** are copies of read-only tools at their defaults, produced by the same code, with the tools kept; `list_resources()` is the inventory. **Progress**: the indexing subprocess records how far it got (per source, chunks done of the total once known) to a file of its own, `griot_index_status` shows it under `job`, and `griot_index_wait` blocks for a bounded time while sending progress notifications. The one gap left worth revisiting is `elicit_url`; the rest are correctly absent. The management surface itself is settled and implemented (the server's own `list_tools()`, `list_prompts()` and `list_resources()` are the inventory; a confirmation policy; secrets and settings deliberately excluded). Full mapping: [docs/mcp-capability-coverage.md](docs/mcp-capability-coverage.md). The end-to-end validation above produces the evidence of what agents actually use, and `tool_calls` records it, resource reads included (under their URI), which is also what will say whether the resources earn their place next to the tools.

- **Retention for quality checks.** Searches and MCP tool calls are kept `GRIOT_LOG_RETENTION_DAYS` days, and indexing runs the last `GRIOT_RUN_RETENTION` of each repository and source (see the changelog). Quality checks are still kept forever, on purpose: they are the pass-rate trend, a few rows a week at most. Revisit only if that table ever grows at a real rate.
- **Curated test cases from real queries: what is left.** `griot golden-set review` offers questions asked more than once and vector searches that scored in the bottom quarter of their collection, and a person picks the right result at a terminal; the case keeps the mode of the search it came from, and nothing is written into the index (the constraint behind the rejected hash mirror below). Two signals were left out. Whether the vector and keyword rankings disagree: a hybrid search logs only the fused results, so this needs both rankings in the log first. Whether the agent actually used a result in its answer: griot never sees the answer. No MCP tool either: the point of the review is that a person says which result was right.
- **A multilingual default embedding profile.** A measurement on 2026-10-06, on three non-English repositories of different kinds, none of them this one, found vector search weak on descriptive questions: MRR@10 about 0.30, against 0.64 to 0.67 on the English repositories measured. Hybrid gained 0.12 MRR and 0.22 recall@10 over vector there, and keyword alone was slightly ahead of hybrid on descriptive MRR (0.46 against 0.43). The likely reason is that the default profile is an English code model. Not scheduled: changing the default re-embeds every user's index, so a multilingual candidate would first be measured the same way (`scripts/measure-search-modes.py`), on English and non-English repositories alike.
- **The file path in the embedded text: measured, not adopted.** Prefixing each code chunk with `repo/path` before embedding is a known way to help queries that name a file. Measured on this repository (1,150 chunks, 35 queries with a known target file): with a small general model the mean reciprocal rank went from 0.49 to 0.59; with the default code model it went from 0.67 to 0.69 overall, up for queries that name the file (0.71 to 0.79) and down for queries about content only (0.63 to 0.57). Within noise on the default model, and the price is embedding every code chunk of every user again. Worth measuring again with a curated golden set on a paid profile before reopening.
- **Rejected: mirroring content hashes into SQLite.** Tempting, because `_split_pending()` does a Qdrant round-trip per batch to compare hashes, and a local table would be faster and would work even while another process holds the collection. Rejected because it creates a SECOND source of truth about the same fact: if the two diverge — a failed write, or a bulk cleanup of stale points — the mirror would report "unchanged" for a point that no longer exists. That is exactly the failure class this project has already been bitten by: an id-scheme mismatch that silently duplicated an index while every run reported success. Asking the store that actually holds the data is self-consistent by construction, and this is not a bottleneck anyway (a full reindex is dominated by embedding, not by the local read). A mirror used as an AUDIT reference is a different proposition — divergence would be the signal rather than a silent lie — but that is not this.

- **Ship as a Claude Code plugin** (`/griot:stats` instead of `/mcp__griot__stats`). A plugin is a thin packaging shell — `.claude-plugin/plugin.json` naming the plugin and listing `commands/*.md`, plus a `.mcp.json` pointing at the `griot mcp` server that already exists — where the plugin name becomes the command namespace. Verified against the official Vercel plugin, which uses both layers at once: `/vercel:env` comes from its `commands/` list, while its MCP server is registered separately through `.mcp.json`. Deliberately NOT scheduled: it is a Claude Code convention, not part of MCP, so it trades portability for integration with one client, and it would be a third distribution channel, next to PyPI and `griot assist install`, to keep in step with every release.

## Later / deferred

- **Embedded local chat** for `griot ask` — in-process GGUF inference (llama-cpp-python) with a small model (e.g. Qwen2.5-0.5B-Instruct or SmolLM2-360M-Instruct), so `ask` can run fully offline. Deferred deliberately: real quality limitations at that size for RAG synthesis, plus a heavy new dependency. Needs explicit demand before building.
- **Watch mode / git hooks for automatic incremental indexing.** Deferred because incremental indexing (by content hash) already makes a manual re-index over an unchanged repo cost nothing — automatic triggering would save a command invocation, not embedding cost. Worth it once "I forgot to re-index before asking" actually happens.
- **Terminal UI (TUI)** — if griot ever grows a UI, it belongs in the terminal, alongside the CLI rather than parallel to it. A graphical front end was tried and removed for duplicating the CLI at a cost that was not worth carrying; the reasoning is in [lessons and debts](docs/lessons-and-debts.md).
- **Indexing manuals, ebooks and sites** next to the code. Everything in griot is keyed by `repo:source_type:key`, and a PDF or a web page has neither a repository nor a history, so it would need a new source type keyed by file hash or URL, plus an extraction pipeline unrelated to the code chunker. Sites would also add a kind of network access that [SECURITY.md](SECURITY.md#what-leaves-your-machine) has no row for today, which makes them a real scope expansion rather than a small addition. Deferred on purpose. The smaller first step, should it come back, would be local files only.
- HTML report export, multiple simultaneous indexes — only if real usage demands them.
